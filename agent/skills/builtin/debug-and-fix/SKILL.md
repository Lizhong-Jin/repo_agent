围绕用户报告的故障建立证据、定位原因、实施必要修复，并验证原问题。
用户的任务范围和明确约束优先；本技能不扩大工具权限或授权提交、发布、回写。
先通过 load_skill 加载 coding 技能，沿用其中的代码编辑、测试和交付约定；
当前上下文已有该技能正文时直接复用。下面补充故障定位与修复的专用流程。

## 复现与定位

- 确认触发输入、实际行为和预期行为。先读报错、相关实现与现有测试；
  按需要使用 search_files、get_symbols、read_file 缩小范围。
  只有缺失信息确实妨碍推进时才询问，并说明已知证据。
- 优先运行最小相关测试或复现命令。结合实际可用工具和项目已有运行方式选择验证方法。
  没有 run_command 或 run_python 时，继续静态定位与允许范围内的修复，明确测试未运行；
  不尝试绕过 local 模式限制启动宿主机命令。
- 区分产品缺陷、测试假设错误、依赖缺失和环境问题。报告观察到的事实与推断，
  不为让测试变绿而删除断言、忽略异常或改变用户要求的行为。

## 修复

- 如果用户只要求解释或诊断，给出原因与修复建议，不修改文件。
- 修复前检查相关文件及已有变更，保留用户工作。优先修正根因，并保持无关行为。
  用可用的编辑或补丁工具做局部修改；遵循仓库现有风格和测试方式。
- 对可能再次出现的行为缺陷，增加能够区分修复前后行为的回归测试。
  小型文案、配置等低影响修正无需机械添加测试。

## 验证

- 重跑原复现及受影响的相关测试。一次有针对性的验证通过后，只有影响范围或新证据
  支持时再扩大测试；不反复重跑同样的检查。
- 修复后用 git_diff（若可用）或重新读取修改位置检查最终变化。
  验证失败则依据错误继续处理；缺少依赖、输入或执行能力时准确说明尚未验证的部分。

## 交付

简洁说明故障原因、修改文件、实际执行的验证与结果，以及必要的未完成事项。
不把静态推断说成运行验证，不把模型正常结束或技能加载成功当成测试通过。
文件在 Docker 副本中时准确说明状态，回写由应用现有流程处理。
