# 可信交付

[文档首页](index.md) · [验证清单](verification.md) · [任务报告](task-reports.md) · [独立工作区](workspaces.md)

可信交付把用户固定的必需检查、实际执行证据和当前候选内容关联起来。执行结束、检查通过、用户接受例外和修改已合并分别记录；模型的完成声明不能设置交付通过。

## 第一版范围

- `report-only` 是新会话和旧快照的默认行为：继续展示任务报告，不增加交付阻塞。
- `strict` 支持 develop 权限下的 local/native，可用于 direct 或 worktree。local 没有命令执行能力，命令检查不能通过；人工检查仍可使用。
- strict 未通过时暂停后续队列；worktree 合并入口还会重新核对交付结论、报告、验收意见和当前内容。
- direct 已经直接写入项目；Windows native 也会逐调用回写。交付受阻不会撤销这些修改。需要保持原项目不变时使用 worktree。
- 第一版拒绝 strict 与 Docker 或只读 review 组合。Docker 现有回写检查和 `check_id` 保持原行为，尚未接入这套任务级交付判定。

## 固定必需检查

先准备 JSON 文件。示例中的命令需要执行环境中已有 pytest 和项目测试依赖；修改为本项目实际的验证命令：

```json
{
  "version": 1,
  "checks": [
    {
      "id": "tests",
      "title": "项目回归测试",
      "kind": "command",
      "command": ["python", "-m", "pytest", "-q"],
      "cwd": ".",
      "expectation": "相关回归测试通过；失败时退出码非零"
    },
    {
      "id": "review",
      "title": "人工审查修改",
      "kind": "manual",
      "expectation": "确认变更满足需求，没有不应提交的内容"
    }
  ]
}
```

```bash
repo-agent --root /path/to/project --new-session --sandbox native \
  --workspace worktree --delivery strict --delivery-policy /path/to/checks.json
```

`--delivery-policy` 表示用户显式信任并选择该文件中的检查，省略 `--delivery` 时隐含 strict。程序不会自动发现或执行仓库中的配置文件。它只固定检查要求，命令仍由模型调用现有工具执行，受原有隔离、超时和取消规则约束；配置不授予额外权限。

检查全部为必需项，strict 至少需要一项，最多 100 项；字段规则复用[验证清单](verification.md#参数与示例)。程序在执行前登记这些检查，模型不需要重复调用 `plan_verification`，也不能重定义相同 ID。模型仍可登记补充检查，它们显示在报告中，但不会替代必需项。任意执行失败、未知进程状态等仍受原执行流程约束。

规则内容保存在会话中，每次任务另保存快照，worktree 状态也固定同一份规则。修改源 JSON 不会改变本会话要求。恢复时可以省略两个参数；显式传入不同规则或尝试降为 report-only 会被拒绝。需要其他规则时新建会话，worktree 也需新建；`/new` 在 direct 会话中继承当前规则。

## 运行、验收与接收

1. 提交开发任务。模型完成修改后应执行全部必需命令检查。
2. 使用 `/report` 或 F3 查看文件变化、检查结果和原始证据。
3. 必需人工项通过原有报告入口验收，例如：

```text
/report 1 --accept review accepted --note "已检查需求和全部变更"
/delivery refresh
/delivery
```

`refresh` 重新计算并保存判定，不执行命令，不补造历史验证。人工意见发生变化后，旧交付结论失效，需刷新；刷新不会自动恢复队列或合并。确认可继续时使用 `/queue resume`。

任务执行状态保持原意：模型正常结束仍记录为 completed；交付状态另行保存。因此可能出现“执行完成，交付受阻”。严格单次任务只有执行完成且交付允许时才返回成功；有必需人工项时通常需后续验收处理。

| 交付状态 | 含义与处理 |
| --- | --- |
| 检查通过 | 必需命令检查通过，必需人工项已接受，无拒绝意见，证据完整且当前内容一致 |
| 受阻 | 存在未执行、失败、超时或待人工验收项目；修复、重验或明确接受例外 |
| 已过期 | 当前内容、Git 候选版本或检查有效性发生变化；需要重新验证 |
| 无法确认 | 执行/清理未确认、扫描不完整、报告/结论缺失或引用不一致；先恢复证据或建立新尝试 |
| 用户接受例外 | 用户明确接受当前检查缺口，原始失败和未验收结果仍保留 |

worktree 最终仍由用户显式接收：

```bash
# 先退出 Agent，释放项目执行锁
repo-agent workspaces review --root /path/to/project --session 1
repo-agent workspaces merge --root /path/to/project --session 1 --review REVIEW_TOKEN --yes
```

新审查令牌不会让过期验证重新有效。合并时同时检查候选内容、交付证据和原目标分支；默认仍只支持原基线上的快进合并。

## 受阻后的操作

```text
/delivery                          # 核对当前交付状态
/delivery recheck                  # 创建新的验证任务，优先于等待项执行
/delivery repair 修复测试失败并重新验证
/delivery accept-exception 已人工核实，暂接受已知失败，后续另行处理
/queue resume                      # 仅在交付允许且执行环境健康时恢复
```

`recheck` 和 `repair` 使用模型及现有工具，会产生新的任务编号、执行尝试、报告和交付结论，保留旧报告。新尝试需重新完成全部必需检查，不借用旧任务的成功记录；人工项也需针对新报告重新验收。`recheck` 的任务要求是不修改项目代码；实际内容变化仍会参与验证有效性判断。没有无限自动修复循环。

这两个入口只允许显式启动验证/修复项，不清除未知进程状态或绕过后端健康检查。验证/修复成功后按正常队列规则继续；失败时再次暂停。达到模型轮数上限仍可用 `/continue`，续接尝试也需完成本次必需检查。

接受例外必须填写原因，并绑定报告、规则、验收意见和候选内容。命令失败仍显示失败，不改写原始报告和账本。执行失败/中断、清理未知、扫描不完整和内容过期不能通过此入口跳过。接受例外后修改文件、重写报告或更新验收意见，原例外不自动适用于新状态。

退出 Agent 后也可操作已保存结论，无需模型配置，不会执行验证命令：

```bash
repo-agent delivery status --root /path/to/project --session 1
repo-agent delivery refresh --root /path/to/project --session 1
repo-agent delivery accept-exception --root /path/to/project --session 1 --note "接受当前已知检查缺口"
```

这些管理命令获取项目执行锁；运行中请使用会话内 `/delivery`。无参数、status 可查看当前结果，其他操作需等待任务及收尾完成。

## 证据、保存与恢复

每次尝试先保存基线与固定检查，再执行任务，收尾时依次保存完整报告、交付结论、会话与队列。交付文件位于同一报告目录：

```text
<项目状态目录>/reports/<session_id>/delivery-<attempt_id>-<内容摘要>.json
```

结论包含规则摘要、机器报告摘要、人工意见摘要、候选内容摘要、任务/尝试身份和阻塞原因。刷新和接受例外生成新文件，队列结果引用最新文件；旧结论保留。报告还记录执行平台、Agent Python 和可用的项目解释器路径，不保存模型凭证。

多文件保存不是整体事务。缺失结论、摘要不匹配、只保存了报告但未确认任务结束，都不能用于通过判定；也不会自动重放任务。报告完整、任务结果已保存而结论写入失败时，可修复存储后 refresh；执行记录已恢复为中断时，应检查文件和进程，再建立新的验证/修复尝试。

报告页展示保存的历史结论，不扫描当前目录伪造历史结果；`/delivery` 和合并入口才核对当前内容。普通 `/queue resume` 不能解除交付阻塞。重启恢复规则与队列暂停状态，工作区保留的严格规则也避免会话文件缺失时退回宽松合并。

## 保证范围

- 命令检查按同一次尝试内的精确 argv 和规范化 cwd 关联，后一次匹配结果优先；检查前后及最终内容必须一致。
- 文件观察仍使用报告的大小、时间预算和排除规则。worktree 额外将准备合并的 Git HEAD/内容树纳入检查指纹，防止已跟踪但被普通报告扫描排除的文件变化漏过判定。
- 这是有边界的观察，不是目录独占锁或系统原子快照。外部编辑器仍可能并发修改文件；当前实现不保证检测所有执行期间的临时修改。
- 不给外部解释器和依赖目录生成完整内容摘要；环境信息是本次执行证据，不是环境可复现证明。变更外部环境后应主动重新验证。
- 退出码 0 不能证明测试覆盖全部需求；模型可以修改项目测试，因此仍需审查测试本身的变化。用户意见不是外部身份认证或多用户审批系统。
