# 执行账本与崩溃恢复

[文档首页](index.md) · [会话管理](sessions.md) · [任务队列](task-queue.md)

执行账本记录每次模型工具调用的意图、开始和返回结果。它与用于诊断的 `trace.jsonl` 分工不同：账本写入是执行的必要条件，写入失败会停止当前任务并暂停队列。日志写入失败仍只影响诊断。

## 查看执行证据

在会话中输入 `/ledger` 查看最近 30 条工具记录。另一终端可以在没有模型配置的情况下查询：

```bash
repo-agent sessions ledger
repo-agent sessions ledger 12 --limit 100
repo-agent sessions ledger 12 --before 300 --limit 100
repo-agent --root /path/to/project sessions ledger 12 --json
```

序号、会话 ID 和名称的选择方式与 `sessions logs` 相同。`--limit` 支持 1–10000，JSON 输出包含完整调用参数、模型工具调用消息、返回消息、已报告效果和身份关联。按最近事件倒序显示；用末条记录的事件序号作为 `--before` 可继续查看更早记录。可通过工具顺序号 `ordinal` 查看一次运行内的调用顺序。

| 状态 | 可以确认什么 |
| --- | --- |
| `intended`，尚未调用 | 该调用意图已保存，尚未提交执行开始记录；本协议没有调用它 |
| `started`，结果待核实 | 已提交开始记录，可能尚未调用、部分执行或全部执行 |
| `returned`，返回结果已保存 | 返回值已提交；工具报告成功或失败另外显示 |
| `uncertain`，结果待核实 | 工具异常退出，已保存错误观察，但不能确定外部效果 |

“返回结果已保存”不表示所有文件修改、后代进程或外部服务效果均已核实。工具返回失败也可能已经产生部分修改。已报告的文件目标、哈希、修改集合、退出码及清理信息按工具实际返回值保存；没有的字段不推断。

## 执行协议

1. 在 Runtime 开始时提交运行身份。队列任务 ID、执行尝试 ID 与会话关联；执行尝试 ID 同时作为 Runtime/诊断日志的 `task_id`。非队列的已保存会话调用也分配独立尝试 ID。
2. 收到并验证模型工具调用批次后，先在一个事务中保存整批意图及原始模型调用消息。
3. 每个工具调用前，单独提交开始记录。
4. 工具返回后提交完整结果和已报告效果，然后才检查取消信号、返回 Runtime、执行后续工具或模型请求。
5. 意图、开始或结果提交失败，停止本次运行。账本异常不会被转换成可继续运行的普通工具失败。未知工具异常也停止运行，保留“待核实”。

SQLite 使用事务和 `synchronous=FULL`；每次连接在事务完成后关闭。账本位于项目私有状态目录的 `execution.sqlite3`，不放在工作区，也不复用上下文压缩档案的清理生命周期。直接创建没有 `SavedConversation` 的 Runtime 仍是无持久化的库用法。

## 与会话快照的关系

快照中的 `ledger_cursor` 表示已通过有效消息历史或恢复证据摘要纳入会话的账本事件序号。后台压缩或队列入队不会盲目把它推进到最新事件。

恢复时，若存在快照之后的工具证据，系统追加有界恢复摘要并暂停队列。不会重放历史工具，也不会把执行了一部分的工具批次伪造成完整的模型对话。完整参数和返回值通过账本查询；恢复摘要最多显示最近 30 条，完整账本保留。

核实未知结果时，先读目标文件，结合已记录的哈希、Git 差异、测试产物和进程状态判断。当前文件相同并不能证明某次调用一定完成。需要重新执行时，由用户明确提出新任务或创建重试；重试具有新的尝试标识，不修改旧记录。

账本缺失、不可读，或者事件序号落后于快照时，恢复失败，不会默默创建空账本覆盖缺口。备份和恢复应同时保留会话 JSON、执行账本及上下文归档；Docker 工作副本另行保留。

## 多文件提交与修复

会话快照、`index` 和 `latest.json` 保留现有格式，使用短时元数据锁串行提交。保存顺序为：

1. 分配递增 `commit_revision`，原子保存完整 `.pending-save` 提交记录。
2. 发布会话快照。
3. 更新索引和默认会话指针。
4. 删除提交记录，确认本次保存结束。

只要 `.pending-save` 存在，它就是未完成发布的恢复依据。下次获取元数据锁时，先校验记录并按同一版本幂等补齐发布，再进行恢复选择、查询或改名。不会根据文件修改时间推测哪份新格式记录更新。过期提交版本、损坏记录、项目身份或序号冲突会明确报错并保留材料。

因此，一次报告失败的保存，可能在后续修复时完成发布。这不代表其中标记的工具一定执行过：执行与否仍以执行账本和现场核实为依据。修复先于外部改名进行，后续快照继续采用索引中的最新名称。

这是可恢复的多文件提交协议，读取者在不持有元数据锁时仍可能看到发布中的中间状态；没有宣称这些文件具备跨文件原子可见性。POSIX 额外同步目录以维持文件替换、删除顺序；Windows 使用现有文件同步与原子替换，断电持久性取决于平台和存储设备，不能等同于已验证的进程崩溃恢复。

## 外部效果边界

数据库事务无法涵盖文件修改、任意命令或远端服务。**外部效果已经发生、结果尚未提交时仍可能崩溃。** 对这样的调用只保留“结果待核实”，缺少成功记录不是重试依据，也不承诺恰好执行一次。

账本及恢复命令不会自动回滚文件、结束未知进程或运行核实命令。配置 API Key 不作为运行身份保存，但调用参数、文件内容和命令输出可能包含敏感数据，应按会话私有资料保护；JSON 导出包含原始数据。

## 实现边界与验证

`agent/execution_ledger.py` 管理事务与查询，`host_support/execution_receipt.py` 提供结果回执作用域及致命持久化异常。Runtime 负责批次意图和调用身份，分派器在返回后的取消检查之前同步发送回执。工具实现和 TUI 不直接操作 SQLite。

`tests/test_execution_ledger.py` 覆盖事务回滚、各写入点故障、取消时结果先落盘、未知工具异常、缺失账本，并在独立子进程中于意图、开始、外部效果及结果提交阶段强制退出。另有会话、索引和指针发布中途退出后的修复测试。它们已纳入跨平台契约 CI。
