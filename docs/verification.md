# 验证清单与人工验收

[文档首页](index.md) · [任务报告](task-reports.md) · [工具参考](tools.md)

验证清单把预期检查与实际执行证据关联起来。模型回答结束、检查命令成功和用户验收通过是不同结论，应分别查看。

需要将检查结果用于暂停队列和限制工作区合并时，启用[可信交付](delivery.md)。严格模式的必需检查由用户显式提供并在会话中固定，宿主在每次执行前登记；模型只能追加补充项。

## 登记与结果匹配

对需要验证的代码任务，默认系统提示引导模型先调用 `plan_verification` 登记检查，再执行命令。每项包含：稳定 ID、名称、预期行为、类型（`command` 或 `manual`）。命令检查还包含 argv 数组和相对工作目录。任务内最多 100 项；同一 ID 的重复登记幂等，修改检查内容必须用新 ID，旧检查与结果保留。

报告只关联**同一任务执行尝试内，登记之后执行的 `run_command`**：argv 必须完全一致，工作目录按规范化后的相对路径匹配。任意成功命令、其他目录的同名命令、其他任务的结果、登记前的历史命令都不能充当该项证据。多次执行保留全部记录，最近一次结果决定当前检查状态。

状态包括：尚未执行、检查命令通过、失败、超时、文件变化需重新验证、结果未确认、待人工检查。检查命令通过要求退出码为 0、无清理未确认标记，并且检查前后和任务结束的快照范围完整且内容一致。命令必须自行包含有效断言；程序不证明命令确实覆盖了声明的所有预期行为。`run_shell`、`run_python` 仍在原始执行记录中展示；要关联清单，可改用 `run_command` 调用相应解释器或项目测试脚本。

模型只能提出计划，不能设置检查结果或用户验收状态。命令结果与用户验收分别显示。例如，一个命令失败的项目即使用户填写“确认通过”，原始失败仍然可见。

## 参数与示例

`plan_verification` 的参数为 `items` 数组。下面是模型调用示例；它只登记计划，不会运行其中的命令：

```json
{
  "items": [
    {
      "id": "unit-tests",
      "title": "项目单元测试",
      "kind": "command",
      "command": ["python", "-m", "pytest", "-q"],
      "cwd": ".",
      "expectation": "相关回归用例通过，失败时返回非零退出码"
    },
    {
      "id": "session-switch",
      "title": "人工检查会话切换",
      "kind": "manual",
      "expectation": "切换后名称、历史与输入状态符合预期"
    }
  ]
}
```

之后需在支持执行的后端调用 `run_command`，保持完全相同的 `command` 与规范化后的 `cwd`。测试依赖须事先准备；local 和只读审查都不能因为登记了命令而获得执行权限。

| 字段或限制 | 规则 |
| --- | --- |
| `items` | 每次 1–20 项，同一次任务最多 100 项 |
| `id` | 1–64 个英文字母、数字、下划线或连字符；同一调用内唯一 |
| `title` / `expectation` | 去除首尾空白后分别为 1–200 / 1–2000 字符 |
| `kind` | `command` 或 `manual`；人工项不能传 `command`、`cwd` |
| `command` | argv 数组，1–128 项，首项非空；每项最多 8192 字符，总计最多 32768 字符，不含 NUL |
| `cwd` | 默认 `.`，必须位于执行工作区内；拒绝绝对路径、Windows 盘符及规范化后越界的路径 |

不接受结果或验收字段。修改既有 ID 的内容会失败，应使用新 ID；重复完全相同的登记不会抹除原结果。

## 用户验收

```text
/report 3 --accept session-switch accepted --note "已人工切换并确认恢复内容"
/report 3 --accept session-switch rejected --note "切换后名称显示不正确"
/report 3 --accept session-switch pending --note "等待修复后复查"

repo-agent sessions report 2 --task 3 --accept session-switch accepted --note "人工复查通过"
```

必须提供备注。仅能验收已完整保存的报告中的现有项目。验收意见追加保存在同目录 `reviews-<attempt_id>.json`，不会重写机器报告或执行账本；JSON 导出保留意见历史。意见绑定报告内容摘要，报告内容改变后旧意见不自动用于新版本。

此入口记录 UI/CLI 操作者提供的意见，不进行外部身份认证，也不是安全审批系统。模型工具不提供验收接口。人工意见针对报告中的历史版本，不代表此后磁盘文件一直未变。重试和续接任务使用各自的清单与报告，不能跨任务借用通过记录。

## 与 Docker 回写检查的区别

`plan_verification` 的 `id` 属于任务报告；Docker 进程工具的 `check_id` 用于跟踪自动回写前的失败与成功重试，两者互不替代。报告中的人工验收也不会触发 `/apply`、解除失败阻塞或自动合并工作区。

Docker 收尾时实际运行的宿主验证另以 `host_final_verification` 保存，不伪装成模型调用，也不借用旧任务的验证文件。回写条件见 [Docker 沙箱](../sandbox/README.md)。

## 观察范围与限制

检查有效性依赖任务报告中的有界文件快照。排除目录、扫描预算和未知状态见[报告限制](task-reports.md#保存恢复与限制)。当前比较整个观察范围，不做测试依赖分析或自动重验；生成文件也可能使检查变为需要重新验证。验收针对已保存的报告版本，不保证之后的磁盘状态不变。
